# Belt XP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each built building earns XP from real results and levels 1–100, with a visible upgrade in the 3D scene every 10 levels, a Belt XP bubble on the belt and an XP bar in each building view.

**Architecture:** The backend works out XP on the fly from the tables that already record each result (no ledger), and adds only two small append-only/upsert tables: profile refreshes (the one event with no history today) and what the page has already shown ("seen" level, celebrated upgrade). One read route and two write routes serve it. The frontend shows the numbers, grows each building from a fixed ladder of tinted pieces, and plays a level-up moment once per upgrade.

**Tech Stack:** Python 3 + FastAPI + SQLite (STRICT tables, migrations in `src/aicity/migrations/`), pytest; React + TypeScript + React Three Fiber / three.js, `node --test` for pure logic.

**Spec:** `docs/superpowers/specs/2026-11-27-belt-xp-design.md` (read it first; this plan argues from it).

## Global Constraints

- No currency, no streaks, no decay: XP and levels never drop for inactivity. Undo follows the record ("XP follows the record as it now stands").
- Displayed level never goes below `celebrated_tier × 10`.
- Levels 1–100 per building; an upgrade at every 10th level (tier = level // 10, 0–10).
- Belt level = sum of all nine buildings' levels ÷ 9 (integer division), unbuilt = 0, shown as at least 1.
- XP displays are counts only: no money amounts, task titles, platform names or career text. `/api/xp` needs no Touch ID (same rule as the counts-only badges).
- Only built buildings earn: `planner`, `finance`, `jobs` now; `career` rules exist but are switched off until Flight School's screens ship.
- Building XP bar shows at `/b/<id>` only, never at `/b/<id>/screen`. Belt XP bubble shows at `/` only.
- Daily caps use the Mac's local day.
- All glow/motion amounts for growth pieces go in `frontend/src/belt/look.ts`.
- Growth placement is fixed (no randomness that changes between reloads; seed any variation from the building index).
- Growth must not cover the robot, desk or screen in the building view, nor belt click targets.
- Never touch `src/aicity/security.py`. No network calls, no AI, no new dependencies.
- Code uses generic building IDs; display names come from `/api/buildings`.
- Repo is public: no personal data in fixtures, sample data or comments.
- **Live runs never touch real data.** Never use port 8765 (the installed app) or the default data folder `~/AI-City-Data`; never run `scripts/app.py`. A live run uses a throwaway data folder under the session scratchpad (`AICITY_DATA_DIR` set inline on that one command, never exported before a commit, because the commit hooks read the real data folder) holding a copy of `settings.example.toml` as `settings.toml`, in Sample mode, on port 8766 (set `aicity.config.PORT = 8766` in a small launcher kept in the scratchpad before the app is created). Live frontend checks use `npm run build` served by that backend, not the Vite dev server (its proxy points at 8765). `DELETE FROM xp_seen` and the like only ever run against the throwaway Sample database.

## Review Focus

1. **A reopened to-do or an un-marked gym block** must lower XP but never the shown level below an already-celebrated upgrade. Pinned in Task 2 (`test_undo_lowers_xp_but_not_below_celebrated`).
2. **Caps by local day, not UTC**: a to-do done at 23:30 local time (next day in UTC) counts toward the local day's cap. Pinned in Task 1 (`test_cap_uses_local_day`).
3. **Several upgrades waiting at once** (e.g. backfill or a long absence) play as one moment that ends at the newest stage, then never again. Pinned in Task 10 (`multiple pending tiers play once to newest`).
4. **Switching Personal ↔ Sample** must not carry seen/celebrated state across: each database has its own. Pinned in Task 3 (`test_seen_state_is_per_database`).
5. **Settings file missing** must answer 503 like every route, not crash or show made-up routines. Pinned in Task 3 (`test_xp_without_settings_is_503`).
